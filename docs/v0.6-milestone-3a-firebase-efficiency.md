# v0.6 Milestone 3A — Firebase efficiency

Applies on top of Milestone 2 Exam Command Center. No UI, Firebase rules, schema, indexes, credentials, migrations or billing-plan changes. Deploy backend before the frontend where separately deployed (the new endpoint is additive and the old endpoint remains supported).

## Changes
- Automatic workspace refresh on browser visibility return now requires 30 minutes since the last successful snapshot; no periodic workspace polling was introduced. Manual refresh, initial load, immediate mutation saves and existing snapshot reconciliation remain unchanged.
- Scope transaction queries by existing equality fields (course, semester, resource or item), keeping per-user paths and the workspace guard. Server-generated UUIDs use create-only transaction writes without one existence lookup per new activity. An empty staged transaction does not increment the guard.
- The compact Focus overview reads the recent five only if the current-week query contains fewer than five valid completed sessions. Retain the existing lifetime aggregate and active-session guard. Remove duplicate course lookups when starting Focus.
- Add PATCH `/api/items/{identifier}/with-successor` to return a completed task and its next occurrence (if present). The previous PATCH contract is unchanged. The web client merges those records instead of reloading all items.
- Optional development diagnostics: set `STUDYHUB_DB_DIAGNOSTICS=1` for a local backend configured with a test Firestore project. Disabled by default and when VERCEL is set. Log route templates, duration, point lookups, query documents and staged/direct operations; warn on estimated serialized document sizes >=256 KiB and >=512 KiB on instrumented writes. No diagnostic documents, user IDs or payloads logged. Counts are partial estimates, include attempted transaction work, not actual billed reads or committed writes; empty queries, index charges and retries affect billing. JSON size is not exact Firestore document size. SQLite is not instrumented for Firestore counts. No live database scan is performed.

## Measurements and tests
Synthetic adapter scenario: 4 courses, 234 activities in the other three courses, 78 generated activities in empty target course.

| Operation | Baseline document lookups | After | Writes before/after |
|---|---:|---:|---:|
| First generation | 236 | 2 + one empty query | 79/79 |
| Repeat generation | 314 | 80 | 1/0 |
| Ordinary activity completion | 2 | 2 | 1/1 |

Firestore bills a minimum read for an empty query, so first generation is approximately 3 reads before other billing factors. The counts are measured on a fake adapter, not production. The 30-second to 30-minute threshold reduces the theoretical maximum visibility-triggered refreshes by 98.3%, not total production reads.
